# Hosted prototype: deploy and run

The prototype is three Render web services defined in [`render.yaml`](../../render.yaml). How it fits together and why is in `docs/decisions.md` (D-DEMO-HOSTING).

| Service | What it serves | Public? |
|---|---|---|
| `onebridge-demo-api` | identity, organization and cards in one process (`scripts/demo-server.mjs`), demo data seeded on every start | Only through the two apps below |
| `onebridge-demo-app` | Admin dashboard. Proxies `/svc/*` to the API so sessions survive a reload | Behind a shared passcode |
| `onebridge-demo-cards` | Visitor cards, short links (`/r/<code>`), vCards, share-back | Yes, anyone with a card link or QR |

**Demo data only.** The API uses the fake one-time-code provider (code `123456`) and an in-memory database that resets on every restart. Never add real customers, phone numbers or leads.

## 1. Deploy (one time)

1. Push the branch to GitHub.
2. In Render: **New → Blueprint**, pick the repository and branch. Render reads `render.yaml` and proposes the three services.
3. Fill in the secrets it asks for:

   | Variable | Where | Value |
   |---|---|---|
   | `ENCRYPTION_KEY` | api | 64 hex characters (`openssl rand -hex 32`) |
   | `REVALIDATION_SIGNING_SECRET` | api **and** cards | The same random string on both, 32+ characters |
   | `DEMO_RESET_KEY` | api | A random string; only presenters need it |
   | `DEMO_ACCESS_PASSCODE` | app | The passcode you send to invitees |

   `JWT_SECRET` and `INTERNAL_SERVICE_KEY` are generated by Render.
4. If Render gives the services different host names from the ones in `render.yaml` (for example because a name was taken), update `APP_URL`, `WEB_PUBLIC_URL`, `API_PROXY_TARGET`, `NEXT_PUBLIC_WEB_PUBLIC_URL` and `CARDS_SERVICE_URL` to match, then redeploy. `NEXT_PUBLIC_*` values are built into the app, so the app must be rebuilt after changing them.
5. Wait for the API health check (`/healthz`) to turn green. The first start downloads MongoDB and seeds the demo company, which takes 1–2 minutes.

Plan: the blueprint uses the **Starter** plan so services do not sleep. On the free plan each service sleeps after 15 minutes idle and the first visit takes 30–60 seconds; open every link a few minutes before a meeting if you use it.

## 2. Check it works (5 minutes, before every meeting)

1. Open the app URL. Enter the passcode. Tap **Open the demo company**. The overview shows Sahyadri Steel Works with 7 of 8 cards live and 4 leads.
2. Reload the page. You stay signed in. (If you are sent to sign-in, the cookie path or proxy is wrong: check `COOKIE_PATH=/svc/identity/auth` on the API and `API_PROXY_TARGET` on the app.)
3. Cards → Rohit Deshmukh → the QR image appears. Scan it with a phone: Rohit's card opens on the cards URL.
4. On the phone: **Share your details back**, send a test lead. In the dashboard, **Leads** shows it within a few seconds.
5. Cards → change a job title → **Save changes** → reload the card on the phone: it shows the new title.

## 3. Reset the demo

To wipe changes and start from fresh demo data:

```bash
curl -X POST -H "X-Demo-Reset-Key: <DEMO_RESET_KEY>" https://onebridge-demo-api.onrender.com/demo/reset
```

The API restarts and reseeds in about a minute. Restarting the API service from the Render dashboard does the same.

## 4. Run the same setup locally

```bash
pnpm --filter "@onebridge/shared" --filter "@onebridge/api-contracts" run build
```

```bash
pnpm --filter "@onebridge/identity" --filter "@onebridge/organization" --filter "@onebridge/cards" run build
```

Then start the `demo-api-local` and `demo-app-local` configurations in `.claude/launch.json` (API on :8080, dashboard on :3002 with passcode `sahyadri-demo`). For everyday development use `pnpm dev` instead.
